# Wrike 타임로그 상세 가독성 RCA

## 분류

기존 `Ctrl+Alt+W` 날짜 상세의 사용자 의도는 유지하면서 표시 계층과 읽기 영역을 복구·보강하는 변경이다. 새로운 데이터나 편집 capability를 추가하지 않으므로 `hotfix/v0.22.3` lane의 표시 polish/hotfix로 분류한다.

## 의도한 계약

- 선택한 날짜의 실제 Wrike 기록 합계와 각 기록의 티켓, 기록 시간, 코멘트를 빠르게 확인한다.
- 긴 기록은 상세 영역을 스크롤해 확인한다.
- 제목 조회 중·조회 불가·기록 없음은 실제 빈 기록과 구분한다.
- 상세 본문과 제목은 기존처럼 세션 메모리에서만 사용하고, Wrike 조회·캐시·날짜 선택·스크롤 보존 계약은 바꾸지 않는다.

## 현재 동작과 관찰된 차이

기존 `_selected_detail_parts`는 한 `Text` 위젯에 다음 정보를 연속 문자열로 합쳤다.

```text
티켓 제목 · 시간
코멘트
티켓 제목 · 시간
코멘트
```

시각적으로는 제목 합계만 굵게, 코멘트만 회색 들여쓰기로 표시했고 상세 `Text` 높이는 `5`행으로 고정되어 있었다. 첨부 화면에서 확인된 증상은 다음과 같다.

- 긴 티켓 제목이 먼저 줄바꿈되어 시간 정보가 제목 끝에 묻힌다.
- 티켓과 코멘트 사이에 안정적인 필드 경계가 없어 한 항목이 끝났는지 다음 항목이 시작됐는지 빠르게 판별하기 어렵다.
- 두 건 이상의 기록은 고정 5행 뷰포트에서 첫 항목 일부만 보이고 다음 항목이 잘린 것처럼 보인다.
- 비동기 상세가 빈 상태에서 실제 행으로 바뀌어도 위젯 높이는 같은 구조 안에서 갱신되지 않는다.
- 헤더의 `티켓 / 시간 / 코멘트` 설명은 본문을 설명하지만 실제 본문에는 해당 필드 표식이 없어 인지 부하를 줄이지 못한다.

## 근본 원인

1. 데이터 모델은 `TimelogDetailRow`로 티켓·분·코멘트를 이미 분리하고 있었지만, UI 경계에서 다시 한 줄 문자열로 평탄화했다.
2. 시간과 티켓 제목을 같은 제목 태그에 넣어 긴 제목이 시간의 시각적 우선순위를 빼앗았다.
3. 코멘트가 별도 블록이 아니라 단순 줄바꿈과 회색 태그에 의존해 기록 간 경계가 약했다.
4. `Text(height=5)`가 데이터 양과 무관하게 고정되어, 긴 제목과 복수 기록을 수용할 최소 읽기 공간이 없었다.
5. 상세 데이터가 나중에 도착하는 정상적인 loading → available 전환을 구조 재생성으로 취급하지 않아 높이도 함께 재계산되지 않았다.

## 개선 내용

- 상세 헤더를 짧은 `선택 날짜 타임로그`로 정리하고, 본문에서 필드 의미를 직접 표시한다.
- 합계에 기록 건수를 함께 표시한다.
- 각 기록을 `기록 N · HH:MM` 헤더, `티켓`, `코멘트` 블록으로 렌더링한다.
- 시간만 별도 색상·배경 태그로 강조해 긴 티켓 제목과 독립적으로 먼저 인식되게 한다.
- 티켓 제목은 굵게, 코멘트는 더 깊은 들여쓰기와 여백으로 표시한다.
- 상세 `Text`는 빈/loading 상태 4행, 한 건 8행, 복수 기록 최대 12행으로 데이터 양에 따라 읽기 영역을 확보하고, 그 이상은 기존 스크롤로 처리한다.
- 초기 빈 상세가 실제 행으로 바뀌는 갱신에서도 같은 위젯의 높이를 재계산한다.
- 기존 날짜 선택, 상세 스크롤 앵커, 제목 비동기 갱신, 실제 시간 상한(24시간 cap 없음), 세션 전용 데이터 보관은 변경하지 않는다.

## 검증 경계

- 직접 영향 범위: `WorktimeQuickPanel._selected_detail_parts`, 상세 `Text` 구성·태그·높이 갱신.
- 선택 테스트: `tests.unit.test_wrike_worktime_panel`, `tests.unit.test_qa_wrike_timelog_details`.
- 고정한 회귀: 항목별 필드 순서·건수·시간 표시, 긴 제목/코멘트의 존재, loading 후 행 도착 시 높이 증가, 기존 날짜 선택·스크롤·제목 갱신 동작.
- 제외: Wrike API fetch, 세션 캐시 저장, 전역 hotkey, packaged EXE, 실제 서로 다른 Windows DPI 모니터 전환. 이 변경은 그 경로를 수정하지 않는다.

## 검증 결과

- `python -m unittest tests.unit.test_wrike_worktime_panel tests.unit.test_qa_wrike_timelog_details tests.unit.test_qa_wrike_worktime_panel_native`: 70개 통과.
- 대상 모듈 `compileall`과 `git diff --check`: 통과.
- 실제 Tk 합성 fixture에서 초기 빈 상태, 기록 로드 직후, 상세 하단 스크롤 상태를 캡처해 가로 잘림·필드 순서·조작부 노출을 확인했다.
- 기존 `scripts/qa_wrike_worktime_panel_native.py --scenario full`은 현재 branch와 변경 전 물리 worktree에서 모두 `native Tk <Enter> delivery was not observed within 1500ms`로 중단됐다. 이번 타임로그 렌더링과 무관한 포인터 이벤트 검증이며, 이 환경에서는 native smoke를 통과로 주장하지 않는다.
