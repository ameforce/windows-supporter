# 작업표시줄 오버레이 화면 스레드 점유 hotfix

## 의도와 변경 분류

- 의도한 계약: 작업표시줄 오버레이의 위치 감시 틱은 입력이 바뀌지 않으면 캐시된 폭 계산을 재사용하고, 배율 하한은 실제로 잃었을 때만 다시 적용한다(`_reassert_overlay_text_scaling` 문서 주석의 계약).
- 현재 동작: 앱이 켜져 있는 동안 화면 스레드가 CPU 코어 하나의 약 77%를 계속 쓴다. 화면 스레드에 보낸 메시지의 응답이 중간값 86ms, 상위 10% 312ms, 최대 455ms로 밀린다. 그래서 AI 사용량 탭을 포함한 모든 창이 느리고 스크롤이 끊긴다.
- 차이: 배율 하한 확인이 틱마다 "하한을 잃었다"고 오판해 캐시를 비운다.
- 판정: 기존 계약의 결함 복구이므로 `hotfix/v0.33.13`으로 분류한다.

## 근본 원인

실행 중인 v0.33.12(프로필 8개)의 화면 스레드를 20초 동안 표본 추출했다. 표본의 81.5%가 오버레이 위치 감시 틱(`_geometry_monitor_tick`)이었다. 그중 87%가 이름에 `cached`가 붙은 폭 탐색 함수(`_preferred_width_for_rows_cached`)의 본문, 즉 캐시 누락 경로였다.

1. 오버레이는 글꼴 배율 하한을 `96/72 × 1.25 = 1.6667`로 설정한다.
2. Tk는 `tk scaling`을 화면의 밀리미터 크기로 환산해 저장하므로, 다시 읽으면 96dpi에서 `1.66626`이 나온다.
3. 틱마다 도는 `_reassert_overlay_text_scaling`은 `current >= floor - 1e-9`로 비교한다. 0.04% 차이도 "하한 미달"로 판정해 `_apply_overlay_base_ui_scaling`을 다시 부른다.
4. 그 함수는 배율을 다시 쓰고 `_set_overlay_text_width_scale`을 부른다. 이 함수는 값이 같아도 폭 캐시와 글꼴 측정 캐시를 모두 비운다.
5. 비워진 캐시 때문에 300~900px 폭 탐색 전체(약 300ms)를 다시 한다. 좌우 오버레이 두 개가 0.5초마다 이를 반복한다.

같은 설정과 저장된 사용량 값으로 재현했을 때, 틱 1회가 평균 325ms 걸렸고 틱마다 배율을 다시 썼다. 실제 앱의 상위 10% 응답 지연(312ms)과 일치한다.

## 수정

- 배율 비교에 Tk 반올림 허용치(`_TK_SCALING_TOLERANCE = 0.01`)를 둔다. 하한 확인과 이미 적용된 목표의 판정 모두에 적용한다.
- `_set_overlay_text_width_scale`은 폭 배율이 실제로 바뀔 때만 캐시를 비운다. 캐시 비우기는 `_clear_overlay_width_caches`로 모은다.
- 배율을 실제로 다시 쓸 때(하한을 정말 잃었다가 복원할 때 등)는 폭 배율이 같아도 캐시를 비운다. 글꼴 측정값이 `tk scaling`을 따르기 때문이다.
- 글꼴 측정기 설치는 새 글꼴에 맞춰 캐시를 비우되, 폭 배율을 1.0으로 되돌리지 않는다. 앱이 쓰는 96dpi에서는 지금까지 틱마다 다시 설정되어 실제로 쓰이던 폭 배율 1.25를 그대로 유지하므로 오버레이 모양은 바뀌지 않는다.

## 결과

| 조건 | 수정 전 | 수정 후 |

| 재현 틱 1회 평균 | 325ms | 0.8ms |

| 폭 캐시 적중 | 0회 | 38회 |

## 검증 범위

Tk 반올림을 흉내 낸 가짜 루트에서 틱이 배율을 다시 쓰지 않고 캐시를 비우지 않는지 확인한다. 반올림 범위 안의 배율 재적용이 값과 폭 배율을 유지하는지, 같은 폭 배율의 재설정이 캐시를 지키는지, 실제로 잃은 하한을 복원할 때는 캐시를 비우는지도 확인한다. 측정기 설치 후 폭 배율이 유지되는지 검증한다. 오버레이, 다중 모니터, 좌우 창, 작업표시줄 대상, 복구, 다중 모니터 관리자 시험 468건을 실행한다.
