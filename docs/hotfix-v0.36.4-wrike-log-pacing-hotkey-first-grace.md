# wrike.log 근무시간 조회 줄 빈도 정리와 핫키 먼저 순서의 유예 표식

## 분류와 계약

- 의도
  1. `wrike.log`는 휴게 복귀 질문이 보이지 않을 때 원인을 사후에 바로 확인하는 진단 로그다(v0.36.2). 한없이 커지지 않도록 2MiB 상한과 백업 3개로 회전한다(v0.36.3). 이 계약은 회전 보관 기간 안에 단계 로그(`break return:`)가 남아 있어야 성립한다.
  2. 질문을 띄운 같은 키 입력에 감시자와 핫키가 한 번씩 반응하므로 그 직접 열기 한 번만 패널을 닫지 않는다. 사용자가 두 번 누르면 두 번째는 패널을 닫는다(v0.36.2, v0.36.3). 핫키 작업과 입력 감시자는 어느 순서로 처리되어도 같은 결과여야 한다(패널이 이미 열려 있던 경우는 `알려진 한계`).
- 기존 동작
  1. 모니터는 5초마다 근무시간 기록을 읽고, 읽을 때마다 `authoritative contact timelogs: N entries, P pages` 줄을 남겼다. 2026-09-09부터 2026-10-16까지의 `wrike.log.1`(48,066,758바이트)에서 이 줄이 575,467줄, 43,115,981바이트로 바이트 기준 약 90%였고, 줄의 값이 바뀐 것은 451번(하루 평균 약 12번)뿐이었다. 회전 상한에서는 현재 속도로 약 6일치만 남아 오래된 `break return:` 단계 로그를 볼 수 없었다.
  2. 핫키 작업이 입력 감시자(0.5초 주기)보다 먼저 처리되면 핫키가 패널을 먼저 연다. 이어서 감시자가 질문을 띄울 때 실제 패널의 `show()`는 이미 보이는 상태에서도 `True`를 돌려줘 유예 표식이 쓰였다. 바로 닫으려는 두 번째 누름이 유예로 흡수되고 세 번째 누름에서 닫혔다(v0.36.3 최종 검토 자문 R-1, v0.36.3 문서의 `알려진 한계`).
- 차이: 1은 진단 로그의 보관 계약에 못 미치는 불완전 구현이고, 2는 "직접 열기 한 번만 유예"가 감시자가 먼저인 순서에서만 성립한 불완전 구현이다. 둘 다 새 사용자 기능이나 새 제품 정책이 아니다.
- 판정: 의도한 계약의 복구이므로 `hotfix/v0.36.4` 차선에서 고친다. 새 설정 키, 새 화면, 새 로그 파일은 만들지 않는다.

## 수정 범위

- 근무시간 조회 줄의 빈도(`src/apps/Wrike.py`)
  - 줄 형식과 내용은 바꾸지 않는다(`authoritative contact timelogs: N entries, P pages`와, 모은 항목 수가 예고된 전체 수보다 적을 때 붙는 `, announced M`).
  - 마지막으로 쓴 줄과 같은 줄은 `AUTHORITATIVE_TIMELOG_LOG_REPEAT_SECONDS`(300초)가 지나기 전에는 다시 쓰지 않고, 그 뒤 첫 갱신에서 한 번 쓴다. 항목 수, 쪽 수, 예고된 전체 수가 바뀌어 줄이 달라지면 바로 쓴다.
  - 갱신이 오류로 끝났다면 다음 성공 줄은 이전과 같아도 바로 쓴다. 오류 줄과 함께 읽으면 복구된 시각이 보인다. 시계를 되돌려 경과 시간이 음수가 되는 경우도 바로 쓴다.
  - 오류 줄(`api http error`, `api request failed`와 추적 정보)과 다른 단계 줄은 이전처럼 매번 남긴다. 빈도를 조절하는 줄은 이 한 줄뿐이다.
  - 같은 기간의 기록(2026-09-09부터 2026-10-16)에 이 규칙을 다시 적용하면 575,467줄(43,115,981바이트)이 9,934줄(744,308바이트)이 된다. 하루 평균 약 15,500줄(1,132KiB)이 약 270줄(20KiB)로 줄어, 다른 줄까지 합친 하루 약 30KiB에서는 최대 약 8MiB의 회전 보관량이 약 6일에서 수 개월이 된다.
- 유예 표식(`src/apps/Wrike.py`)
  - `__surface_break_return`가 표시 전에 패널이 이미 화면에 있는지 확인하고, 숨은 패널을 실제로 띄운 표시에서만 `__break_return_raised_at` 표식을 쓴다. 핫키가 먼저 열어 둔 패널, 또는 잠금 해제 때 이미 열려 있는 패널에 대한 표시는 표식을 쓰지 않으므로 다음 직접 열기가 패널을 닫는다.
  - 화면 확인은 `__worktime_panel_on_screen`으로 모으고, 재표시 판단(`__maybe_resurface_break_return`)도 같은 함수를 쓴다(그쪽의 동작은 그대로다). 확인 자체가 실패하면 숨은 패널로 본다(이전 동작).
  - 숨은 패널을 띄우는 표시(감시자가 먼저인 순서), 유예 시간(1.5초)과 한 번만 적용하는 규칙, 질문이 지워질 때 표식을 비우는 동작은 바꾸지 않는다. 패널 구현(`WorktimeQuickPanel`)도 바꾸지 않는다.
- v0.36.2 문서와 v0.36.3 문서의 유예와 로그 설명을 이 변경에 맞춰 정정한다.

## 알려진 한계

- 질문이 올라오기 전에 패널이 이미 열려 있던 경우(다른 이유로 떠 있거나 포인터가 올라가 닫히지 않은 경우)에는 두 순서의 결과가 같지 않다. 감시자가 먼저이면 같은 키 입력의 핫키가 유예 없이 패널을 닫는다. 질문은 남아 있으므로 다음 직접 열기나, 입력이 있을 때의 재표시(120초 간격)로 다시 보인다. 핫키가 먼저이면 그 누름이 패널을 닫고, 이어서 감시자가 숨은 패널을 다시 띄워 표식을 쓰므로 다음 누름이 흡수되고 그다음 누름에서 닫힌다(v0.36.3과 같다).
- 핫키가 먼저 열어 둔 패널에 감시자가 질문을 띄울 때 `WorktimeQuickPanel.show`가 패널을 포인터 기준으로 다시 배치하고 닫힘 타이머를 새로 건다. 이 기존 동작은 바꾸지 않았다.
- 줄 빈도 조절은 실행 중인 프로세스의 기억에 의존한다. 앱을 다시 시작하면 첫 결과를 한 번 다시 쓴다.

## 검증 범위

- 직접 영향 단위시험: `test_wrike_break_return_prompt`, `test_wrike_disabled_lifecycle`, `test_wrike_worktime_panel`, `test_wrike_break_edit_regressions`, `test_wrike_realtime_progress`, `test_monitor_hotkey`, `test_monitor_hotkeys`, `test_runtime_lifecycle`(8개 모듈). 실제 `Tk` 창을 띄우는 `test_wrike_worktime_panel`의 `test_real_tk_*` 5개는 이 변경과 무관한 패널 배치 시험이라 제외한다. 나머지 318개가 통과한다.
- 새 시험 12개를 수정 전 소스(v0.36.3)에 덮어 실행해 대조했다. 9개는 수정 전 소스에서 실패하고 수정 후 통과한다. 나머지 3개(오류 줄은 줄이지 않음, 비교할 수 없는 시각도 줄을 씀, 상태를 물을 수 없는 패널은 숨은 패널로 봄)는 지금 동작을 고정하는 회귀 방지용이라 양쪽에서 통과한다.
- 변이 시험 20개를 직접 영향 시험이 모두 잡았다. 줄을 항상 쓰거나 한 번 쓴 뒤 다시 쓰지 않는 변경, 경계(300초)와 시계 되돌림 조건과 비교할 수 없는 시각의 처리를 바꾸는 변경, 값이 바뀌어도 바로 쓰지 않거나 쪽 수와 예고된 전체 수를 무시하는 변경, 조회 오류와 연락처 확인 실패와 갱신 중 예외 뒤 상태를 지우지 않는 변경, 오류 줄까지 빈도를 조절하는 변경, 유예 표식을 열려 있는 패널에도 쓰거나 아예 쓰지 않거나 열려 있는 패널의 표시가 지우는 변경, 화면 확인을 표시 뒤에 하거나 실패를 흡수하지 않는 변경, 재표시 판단이 열려 있는 패널을 무시하는 변경이다.
- 전체 시험과 화면을 띄우는 시험은 실행하지 않는다. 변경은 파일 로그 한 줄의 빈도와 유예 표식을 쓰는 조건에 한정되고, 패널 구현은 바꾸지 않았다. 직접 소비 모듈을 모두 실행했고, 배포 산출물은 태그에서 한 번 만든다.
