# 휴게 복귀 직접 열기 유예 정리와 wrike.log 회전

## 분류와 계약

- 의도
  1. 질문을 띄운 같은 키 입력에 감시자와 핫키가 한 번씩 반응하는 경우를 흡수하려고 직접 열기 한 번만 패널을 닫지 않는다(v0.36.2). 사용자가 두 번 누르면 두 번째는 패널을 닫는다.
  2. 입력 감시자의 생성 실패와 시작 실패는 각각 로그로 남아, 다음에 질문이 보이지 않을 때 원인을 바로 확인할 수 있다(v0.36.2).
  3. 진단 로그는 한없이 커지지 않는다. 런타임 로그(`runtime.jsonl`)는 이미 2MiB 상한과 백업 3개로 회전한다.
- 기존 동작
  1. 유예 표식(`__break_return_raised_at`)은 유예를 한 번 적용한 뒤에도, 질문에 답하거나 질문이 지워진 뒤에도 남았다. 질문을 띄운 지 1.5초 안에 `Ctrl+Alt+W`를 두 번 누르면 두 번째 요청도 패널을 닫지 못했고, 질문에 답한 직후의 직접 열기도 같았다.
  2. `watcher.start()`가 예외를 낼 때의 로그(`activity watcher start failed`), 예상 밖 생성 실패 로그(`activity watcher creation failed`), 시계를 되돌린 때 유예가 적용되지 않는 조건(`0 <= elapsed`)을 고정하는 시험이 없었다.
  3. `wrike.log`는 회전이 없어 2026-09-09부터 2026-10-16까지 47,962,915바이트(약 47MB)가 됐다. 몇 초마다 `authoritative contact timelogs` 줄이 쌓여 하루 약 1.3MB씩 늘었다.
- 차이: 세 경우 모두 의도한 계약에 못 미친 불완전 구현이다. 1은 한 번의 키 입력에 대한 유예가 이어지는 요청과 답변 뒤까지 번졌고, 2는 계약한 로그와 조건에 시험이 없었으며, 3은 런타임 로그에 이미 있는 크기 상한이 이 로그에는 적용되지 않았다.
- 판정: 새 사용자 기능이나 새 제품 정책이 아니라 v0.36.2에서 정한 계약과 기존 로그 상한 정책의 완성이므로 `hotfix/v0.36.3` 차선에서 고친다. 회전은 새 방식을 만들지 않고 런타임 로그의 상한(2MiB)과 백업 수(3개)를 그대로 쓴다.

## 수정 범위

- 유예 표식 정리(`src/apps/Wrike.py`)
  - 직접 열기가 유예를 적용하면 그 자리에서 표식을 비운다. 같은 1.5초 안의 두 번째 직접 열기는 일반 토글로 동작한다.
  - 질문이 지워질 때(`__clear_break_return_prompt`: 계속 휴게, 손으로 휴게 전환, 끝난 휴게의 질문, 잠금 해제 전 휴게 변경, 거부된 답변 뒤 이미 끝난 휴게, 자동 UI 중지)와 `종료`나 `시간 수정` 답변으로 휴게가 끝날 때(`__finish_break_return`)도 표식을 비운다. 질문이 없으면 유예도 없다.
  - 유예 시간(1.5초), 유예를 적용하는 조건(패널이 보임), 질문을 띄우고 표식을 쓰는 쪽은 바꾸지 않는다.
- `wrike.log` 회전(`src/utils/runtime_lifecycle.py`, `src/apps/Wrike.py`)
  - 런타임 로그의 회전 코드를 `rotate_log_file(...)` 함수로 옮겼다. `RuntimeLifecycle`이 같은 함수를 호출하고, 성공했을 때의 파일 배치(상한 비교, 백업 수, 번호 이동, 상한 이하일 때 유지, 없는 파일, 백업 0개일 때 삭제)는 그대로다. Wrike는 이 함수를 기본값(2MiB, 백업 3개)으로 호출한다.
  - 새 줄이 상한을 넘기면 `wrike.log`를 `wrike.log.1`로 옮기고 기존 백업을 `.2`, `.3`으로 민다. 가장 오래된 `.3`은 버려진다. 보관량은 최대 약 8MiB이고 지금의 기록 속도에서는 약 6일치다.
  - 첫 회전에서 지금의 47MB 파일은 그대로 `wrike.log.1`이 되고 세 번 더 회전하면 밀려난다. 내용은 자르거나 고치지 않는다.
  - 현재 로그를 `<log>.rotating`으로 먼저 옮긴 뒤 백업을 밀고 `.1`로 확정한다. 다른 프로그램이 삭제 공유 없이 파일을 열고 있어 옮기지 못하면 백업을 건드리지 않고, 백업을 미는 도중 실패하면 현재 로그를 되돌린다. 첫 백업 자리(`.1`)가 비어 있으면 사슬을 밀지 않으므로, 마지막 이동이 한 번 실패한 뒤 다시 시도해도 백업이 더 사라지지 않는다. 줄마다 다시 시도해도 백업이 밀려 사라지지 않는다.
  - 이전 회전이 중간에 끝나(프로세스가 끝나거나 되돌림이 실패해) `.rotating`이 남아 있으면 새 회전은 그것을 덮어쓰지 않고 먼저 백업에 넣는다.
  - 이 순서는 `runtime.jsonl`에도 같이 적용되며 실패했을 때만 이전과 다르다.
  - 회전이 실패해도 줄은 그대로 남기고 다음 줄에서 다시 시도한다. 파일을 옮기는 단계와 추가가 겹치지 않도록 쓰는 스레드끼리 잠금으로 차례를 지킨다. 회전 판단에 넘기는 줄 크기는 텍스트 모드 쓰기가 디스크에 쓰는 바이트 수(줄바꿈은 `os.linesep`)다.
  - 줄 형식(`[시각] 메시지`)과 내용은 바꾸지 않는다.
- 시험 빈틈(`tests/unit/test_wrike_break_return_prompt.py`, `tests/unit/test_runtime_lifecycle.py`)
  - 감시자 시작 예외와 예상 밖 생성 실패가 각각 한 줄로 기록된다.
  - 시계를 되돌려 현재 시각이 표식보다 이르면 직접 열기는 패널을 닫는다.
  - 현재 로그를 옮기지 못하는 회전, 백업을 미는 도중의 실패, 마지막 이동의 실패 뒤 재시도, 남은 `.rotating`이 있는 회전, 다른 핸들이 `wrike.log`를 열고 있는 상태(Windows)에서 백업과 줄이 보존되고 줄을 잠금 안에서 덧붙인다.
- v0.36.2 문서의 유예와 로그 설명 두 곳을 이 변경에 맞춰 정정한다.

## 검증 범위

- 직접 영향 단위시험: `test_wrike_break_return_prompt`, `test_wrike_disabled_lifecycle`, `test_wrike_worktime_panel`, `test_wrike_break_edit_regressions`, `test_wrike_realtime_progress`, `test_monitor_hotkey`, `test_monitor_hotkeys`, 그리고 함수를 옮긴 `test_runtime_lifecycle`(8개 모듈). 실제 `Tk` 창을 띄우는 `test_wrike_worktime_panel`의 `test_real_tk_*` 5개는 이 변경과 무관한 패널 배치 시험이라 제외한다. 나머지 305개가 통과한다.
- 새 시험 26개를 수정 전 소스(v0.36.2)에 덮어 실행해 대조했다. 10개는 실패나 오류이고 12개(`test_runtime_lifecycle`의 새 시험)는 `rotate_log_file`이 없어 모듈을 불러오지 못한다. 나머지 4개(감시자 시작 예외, 예상 밖 생성 실패, 시계 되돌림, 상한 아래 줄 추가)는 지금 동작을 고정하는 회귀 방지용이라 양쪽에서 통과한다.
- 변이 시험 24개를 새 시험이 모두 잡았다. 유예를 소비하지 않는 변경, 질문 삭제와 답변 종료에서 표식을 남기는 변경, 시계 되돌림 조건과 창 길이 조건을 빼는 변경, 시작 실패와 생성 실패 로그를 빼거나 이름을 바꾸는 변경, 회전 호출과 잠금과 줄 크기와 덧붙이는 위치와 실패 흡수를 바꾸는 변경, 백업을 먼저 밀거나 되돌리지 않는 변경, 남은 `.rotating`을 마무리하지 않거나 자리를 만들지 않는 변경, 첫 자리가 비어도 사슬을 미는 변경, 회전 함수의 상한 비교와 백업 연쇄와 이동과 0개 백업과 없는 파일 처리를 바꾸는 변경, 런타임 로그가 자기 상한을 쓰지 않는 변경이다.
- 전체 시험과 화면을 띄우는 시험은 실행하지 않는다. 변경은 근무시간 패널을 열고 닫는 판단과 파일 로그에 한정되고, 패널 구현(`WorktimeQuickPanel`)은 바꾸지 않았다. 직접 소비 모듈을 모두 실행했고, 배포 산출물은 태그에서 한 번 만든다.
