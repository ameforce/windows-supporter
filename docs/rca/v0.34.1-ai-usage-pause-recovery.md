## 1. WAIT (`profile_in_use`) 고정

### 원인

- 로그 순서는 모든 사례에서 같았다(`codex-account-1` 9/26 19:10, `Codex 6` 9/26 20:28 등).
  1. 성공 100회 뒤 계획된 worker 교체(`reason=success_count`)가 시작됐다.
  2. `shutdown` 명령이 5초 제한을 넘었다.
  3. Job을 종료했다(`job_empty=true`).
  4. 즉시 새 worker의 `launch_persistent_context`를 실행했다.
  5. Chrome이 `Failed to create a ProcessSingleton for your profile directory`로 거부했다.
- 그 뒤 해당 프로필의 로그가 앱 재시작까지 한 줄도 없었다.
- 유발 조건:
  - Job의 프로세스가 모두 끝나도 Windows ProcessSingleton `lockfile`이 잠시 잡혀 있거나 delete-pending일 수 있다. 백신이나 색인기가 잡은 경우가 그 예다.
  - 실제 Chrome으로 `lockfile`을 공유 없이 잡으면 운영 로그와 같은 오류가 재현된다. Chrome이 약 6초 뒤 거부한다.
  - 같은 프로필로 살아 있는 다른 Chrome이 있으면 Chrome은 보통 이 잠금 오류 대신 기존 창에 명령줄을 넘기는 경로를 탄다(Chromium ProcessSingleton 동작, 이번에 따로 재현하지는 않았다). 그래서 이 오류는 잔여 잠금으로 본다.
  - 재실행 전에 잠금 해제를 기다리거나 다시 시도하는 경로가 없었다.
- 고정 조건:
  - 다중 프로필 관리자 `__is_background_account_paused`가 `paused_profile_in_use` 프로필을 자동 조회 대상에서 뺐다. 뺀 뒤에는 다시 조회를 요청하지 않았다.
  - child는 조회에 성공하거나 로그인·로그아웃할 때만 `profile_in_use`를 지운다.
  - 설정 화면은 이 상태에서 수동 조회 버튼도 막는다. 그래서 문서의 "수동 재조회 때 재시도"도 실제로는 쓸 수 없었다.
  - 단독 monitor tick의 `next_delay = min(interval, 20)`도 `__should_run_background_collection`이 거짓이라 예약되지 않았다.

### 수정

- process driver(`collect`)는 잠금 거부(`profile_in_use`)를 받으면 2초, 4초 뒤 같은 worker에서 두 번까지 다시 실행한다.
  - Chrome을 찾거나 종료하지 않는다.
  - 운영 collect 제한(45초 이상) 안에서 끝난다.
- 관리자는 `paused_profile_in_use`를 자동 조회 대상에서 빼지 않는다. child가 주는 `retry_after_sec` 간격으로 다시 조회한다.
  - 30초(조회 주기가 더 길면 그 주기)에서 시작해 실패할 때마다 두 배로 늘고, 최대 15분이다.
- child의 자동 조회 차단 사유에서 `profile_in_use`를 뺐다.
  - 예약된 재조회가 잠금 거부 없이 브라우저에 닿으면 WAIT를 지운다.
  - 다른 오류로 끝나면 그 오류를 표시한다.
- 설정 화면 문구를 `프로필 사용 중 (잠시 후 자동 재시도)`로 바꿨다. `docs/release-v0.7.0-codex-usage-playwright.md`의 계약 문장도 고쳤다.

## 2. OUT (`cloudflare_challenge`) 고정

### 원인

- `codex-account-2`(Codex 2)는 9/28 02:25:25에 백그라운드 조회에서 `cloudflare_challenge`를 받았다. 그 뒤 `collect auth deferred ... using_last_snapshot=true` 로그 뒤로 앱 재시작까지 조회가 없었다.
  - 재시작 뒤 첫 `manual_login` 확인은 약 8초 만에 정상 조회로 돌아왔다. challenge는 일시적이었다.
- 경로:
  1. `__should_defer_background_auth_error`는 캐시가 있는 백그라운드 `login_required`/`cloudflare_challenge`를 같은 방식으로 처리한다. 둘 다 auth attention을 저장하고 자동 조회를 멈춘다.
  2. 관리자는 auth attention 프로필을 자동 조회에서 뺀다.
  3. attention은 상태 파일에 저장되므로 재시작 뒤에도 남는다.
- 이력:
  - 4e718e3은 이 경로를 "재시도 가능한 백그라운드 인증 확인"으로 만들었다.
  - f6f83f2가 사용자 조치가 필요한 로그인 만료를 드러내려고 attention 고정으로 바꿨다. 이때 edge challenge도 함께 고정됐다.
  - 이후 Claude provider는 edge challenge를 환경성·재시도 대상으로 명시했다(`TRANSIENT`, OUT 금지).

### 수정

- 캐시가 있는 백그라운드(`auto_monitor`, `monitor_tick`) `cloudflare_challenge`는 `TRANSIENT`로 처리한다.
  - 세션과 마지막 snapshot(stale 표시)을 유지하고, 브라우저 context는 닫아 다음 조회를 새로 시작한다.
  - WAIT와 같은 backoff(30초 또는 조회 주기부터 두 배, 최대 15분)로 다시 조회한다.
  - auth attention을 저장하지 않는다.
- 이전 빌드가 저장한 백그라운드 edge challenge attention은 캐시가 있고 로그인 상태면 불러올 때 풀어 준다. 수동 조회에서 생긴 attention과 `login_required`는 그대로 사용자 조치 대상이다(f6f83f2 유지).
- 캐시가 없는 경우와 수동 조회·로그인 경로는 바꾸지 않았다.

## 검증

- targeted unit/e2e: `tests.unit.test_codex_usage_playwright_process`, `tests.unit.test_codex_usage_monitor`, `tests.unit.test_codex_usage_multi_monitor`, `tests.e2e.test_codex_usage_monitor_flow`, `tests.unit.test_codex_usage_ui`, `tests.unit.test_claude_usage_monitor`, `tests.unit.test_cursor_usage_monitor`, `tests.unit.test_ai_usage_contracts`.
  - 새 테스트는 수정 전 코드에서 모두 실패한다. WAIT는 unit 8개와 UI 문구 1개다. OUT은 e2e 2개로, 백그라운드 subtest 4개가 실패한다. 수동 조회 attention 유지 subtest는 수정 전후 모두 통과한다.
- 실제 Chrome 통합(`tests.integration.test_codex_usage_playwright_process_chrome`, headless, 임시 프로필, 로컬 fixture 서버):
  - `lockfile`을 공유 없이 잡으면 Chrome이 운영과 같은 ProcessSingleton 오류를 낸다.
  - 수정 전 코드는 `profile_in_use`로 끝났다. 수정 후에는 잠금을 푼 뒤 같은 조회가 probe를 반환한다.
  - 같은 파일의 `test_actual_renderer_crash_is_classified_and_worker_is_reaped`는 수정 전후 모두 임시 폴더 정리 `PermissionError`(WinError 32)로 실패한다. 기존 환경 문제이며 이번 변경 경로(`profile_in_use` 재시도)와 관계없다.
- 전체 unit/E2E와 실제 앱 창 실행은 하지 않았다.
