## 1. Dashboard 카드가 눌려 잘림

### 원인

1. `_sync_dashboard_scroll_geometry`는 `<Configure>` 처리 중에 `container.winfo_reqheight()`를 읽어
   캔버스 창의 높이를 고정했다. 열 전환이나 상태 줄 재배치로 늘어난 요구 높이는 이후 idle 배치에서야
   반영된다. 높이가 고정된 frame에는 `<Configure>`가 다시 오지 않으므로, grid가 모든 행을 균등하게 줄였다.
   재현값은 다음과 같다. 창 669x425에서 요구 높이 619px가 379px로 고정되었고, 카드 6개가
   요구 74/116px 대신 34/76px로 그려졌다.
2. v0.33.18에서는 연속 `<Configure>`가 우연히 높이를 다시 맞췄다. v0.33.19가 크기 변경이 끝난 뒤
   한 번만 배치하도록 바꾸면서, 원래 있던 이 결함이 계속 남게 되었다. v0.33.18도 첫 열기 직후에는
   같은 잘림이 재현되었다.
3. 첫 맞춤은 두 카드의 자연 폭(627~669px)으로 창을 잡았다. 그런데 2열 기준은 grid 폭 760px이어서,
   다음 `<Configure>`에서 1열로 바뀌었다. 이때 높이 상한(`maxsize`)은 여전히 2열 높이였다.
4. 열 수를 grid 자신의 폭으로 결정했다. 캔버스 창이 뷰포트 폭에 맞춰지기 전의 grid 폭은
   현재 열 수에 따라 달라진다. 그래서 측정용으로 잡아 둔 2열이 창을 보이기 전에 1열로 뒤집혔다.
5. 창을 매핑할 때 같은 크기의 `<Configure>`가 늦게 한 번 더 온다. `_on_root_configure`는 이를
   사용자 크기로 기록했고, 그 결과 첫 맞춤 크기가 그 탭의 크기로 굳었다.
6. Update 탭의 설명 Label은 `sticky="we"`로 카드 폭만큼 늘어났다. `anchor`가 없어서
   한 줄 문구가 가운데에 놓였다.

### 수정

- 스크롤 높이 동기화를 idle 시점에 한 번으로 모은다. geometry 전파(`update_idletasks`)가 끝난 뒤의
  요구 높이로 맞추고, 값이 같으면 다시 고정하지 않는다. 열 전환과 상태 줄 재배치는 이 동기화를 요청한다.
- 열 수는 스크롤 뷰포트 폭에서 좌우 여백을 뺀 값으로 정한다. 뷰포트가 아직 매핑되지 않았으면
  측정용 배치를 그대로 둔다.
- 2열로 측정했으면 선호 폭을 `760 + 2×10 + 스크롤바` 이상으로 보고한다. 그래서 맞춘 창은 2열을 유지한다.
- 창 크기 변경으로 열이 바뀌면 shell이 높이 상한을 새 배치의 콘텐츠 높이로 다시 잡는다.
- 마지막으로 자동 적용한 크기와 같은 `<Configure>`는 사용자 크기로 기록하지 않는다.
  다른 크기가 한 번 오면 이 판정을 해제하므로, 나중에 같은 크기로 되돌리는 조절은 기록한다.
- Update 설명 Label에 `anchor="w"`를 준다.

## 2. AI 사용량 상단 단일 프로필 편집부 폐기

v0.33.19는 프로필마다 만들던 네이티브 버튼을 상단 공용 편집부 하나로 옮겨 위젯 수를 고정했다.
그 결과 연결, 연결 해제, 삭제, 제공자 변경, 프로필별 수집 끄기는 상단에서만 할 수 있었다.
사용자가 상단 영역 폐기를 지시했으므로, 편집부를 없애고 같은 동작을 카드로 옮겼다.

- 카드 제목 오른쪽에 `•••`를 그린다. 공유 Canvas의 text 항목이며 네이티브 위젯이 아니다.
  이 표시를 클릭하거나, 카드를 우클릭하거나(`ButtonRelease-3`), Shift+F10 또는 메뉴 키를 누르면
  탭 전체가 공유하는 `tk.Menu` 하나가 열린다. 메뉴는 처음 사용할 때 만든다.
- 메뉴를 열 때마다 항목을 그 프로필의 변수와 동작 상태에 다시 연결한다. 연결된 프로필의
  `연결`처럼 쓸 수 없는 동작은 비활성으로 보인다.
- 항목은 새로고침, 연결, 연결 해제, 제공자(Codex/Cursor/Claude), 수집, 작업표시줄 표시,
  위로/아래로 이동, 삭제…이다. 확인 창, 4개 표시 한도, 저장 실패 복원, 진행 중 차단 같은
  처리는 기존 처리 함수를 그대로 쓴다.
- 제목 클릭은 선택(파란 테두리)과 드래그 시작을 함께 한다. Ctrl+위/아래 선택 이동도 유지한다.
- 이 문서는 v0.33.19 RCA의 "상단 고정 조작부" 설명을 대체한다.

`•••`는 Segoe UI 자체 글리프이며 제목 줄 가운데에 맞춰진다. U+22EF는 대체 글꼴의 기준선에
붙어 흐리게 보였으므로 쓰지 않았다.

## 3. 업데이트 확인 창이 다른 창 뒤에 뜸

### 원인

- `_ask_update`를 비롯한 updater 대화상자는 `parent` 없이 `tkinter.messagebox`를 호출했다.
  그래서 트레이에서 숨긴 main root가 소유 창이 되었다.
- 주기 확인은 타이머에서 끝나므로, 그 시점에 앱은 전경 프로세스가 아니다. Windows 전경 잠금 때문에
  창이 활성화되지 않았고, 소유 창이 topmost도 아니어서 활성 창 아래에 만들어졌다.
- 재현: 숨긴 root가 소유한 `askyesno` 창은 topmost=False, foreground=False였다.

### 수정

- updater의 모든 대화상자(업데이트 확인, Git 앱 종료, 강제 정리, 안내, 경고)를 숨긴 topmost 임시
  Toplevel이 소유하게 하고, 대화상자가 닫히면 그 Toplevel을 제거한다. Tk 대화상자를 그대로 쓰므로
  대화상자가 떠 있는 동안의 이벤트 처리 방식은 이전과 같다.
- 소유 창이 더 이상 main root가 아니므로 설정 창은 대화상자가 떠 있는 동안에도 사용할 수 있다.
  이때 새 확인이 시작되어 같은 안내가 한 번 더 뜨지 않도록, 확인 창이 열려 있으면 새 확인을 시작하지 않는다.
- 한계: Windows 정책상 백그라운드 프로세스는 키보드 포커스를 가져올 수 없다(foreground=False).
  대신 창이 다른 창 위에 보이며, 클릭해서 응답할 수 있다.

## 4. 업데이트 중 진행 창을 옮기지 못함

### 원인

- 업데이트 helper(`run_release_update_handoff`, `run_update_handoff`)는 진행 창과 모든 업데이트
  단계를 한 스레드에서 실행했다.
- Tk 이벤트는 진행률을 게시할 때만 처리되었다(다운로드 최대 5Hz, installer 대기 10Hz).
  다음 구간에서는 전혀 처리되지 않았다: 기존 앱 종료 대기(최대 25초), 프로세스 정리,
  SHA-256 확인과 백업 복사, 네트워크 대기, 설치 결과 검증.
- 테두리 없는 창의 끌기는 Tk `<B1-Motion>` 처리에 의존하므로, 이 구간 동안 창을 옮길 수 없었다.
- 본 앱의 준비 창도 helper 응답 대기(최대 15초)와 하위 프로세스 정리(최대 3초) 동안 Tk 스레드를 막았다.

### 수정

- helper 진입점(`run_update_handoff_from_argv`)은 `ThreadedProgressUiHost`로 업데이트 작업을 worker
  스레드에서 실행한다. 메인 스레드는 진행 창을 만들고 약 10ms마다 처리한다.
  - worker는 proxy를 통해 진행 상태를 큐에 넣는다.
  - 재시도/닫기 결정은 Event로 전달받는다.
  - Tk는 메인 스레드에서만 사용한다.
- release 모드로 분기할 때도 호출자의 progress UI factory를 넘긴다.
- 본 앱 준비 창: 하위 프로세스 정리와 helper 응답 대기를 worker 스레드에서 실행하고,
  그동안 창 이벤트를 계속 처리한다.
