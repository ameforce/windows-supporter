# Wrike 비활성화와 설정 반영 수정

## 분류와 계약

- 의도: Wrike를 끄면 자동 근무시간 창과 알림이 중단되어야 한다. Background는 다른 기능의 백그라운드 실행을 계속 허용한다. ~~사용자가 직접 여는 근무시간 창은 사용할 수 있다.~~ (v0.36.2 정정: 직접 여는 근무시간 창(`Ctrl+Alt+W`)도 Wrike가 꺼져 있으면 열지 않고 안내만 표시한다. 자세한 내용은 `hotfix-v0.36.2-wrike-disabled-hotkey-break-return-resurface.md`를 따른다.)
- 기존 동작: `monitor_enabled`는 타임로그 모니터링만 중단했다. 활동 감지, 추가근무와 일부 비동기 알림 경로는 해당 값을 검사하지 않았다.
- 차이: Wrike를 꺼도 자동 UI가 노출되고, 화면에 표시된 설정과 저장 상태가 달라질 수 있었다.
- 판정: 기존 비활성화 계약의 누락을 복구하는 hotfix다.

## 확인한 원인

1. `start_background()`가 비활성화 상태에서도 활동 감지를 시작하고, 자동 패널 표시 경로가 비활성화를 검사하지 않았다. 설정을 끈 뒤 취소된 타이머나 이미 시작한 비동기 작업이 완료되는 경우도 처리해야 한다.
2. 설정 화면의 Wrike 스위치는 전체 입력을 350ms 뒤 자동 저장했다. 다른 숫자 입력이 미완성이면 스위치 변경도 저장되지 않았지만 체크 표시는 되돌리지 않았다.
3. 대시보드는 `update_settings()`의 실패 결과를 무시했다. 이미 열린 설정 화면의 이전 체크 값도 갱신하지 않아, 이후 다른 필드 자동 저장이 그 값을 다시 쓸 수 있었다.
4. 저장소의 원자적 파일 교체와 저장 실패 시 메모리 복원은 이미 구현되어 있었다. 다만 파일 저장 중 다른 스레드가 임시 비활성화 값을 읽어 예약 작업을 버릴 수 있었다. 활성화 후보는 저장 파일에만 전달하고, 성공 뒤에 실행 상태로 공개한다.
5. 자동으로 열린 Flex 창을 사용자가 직접 선택해도 자동 소유 상태가 남아 비활성화 시 닫힐 수 있었다. 명시적인 로그인, 동기화와 웹 열기는 창 소유권을 수동으로 바꾸고 늦게 도착한 자동 이벤트도 이를 되돌리지 않는다.

조사 시 설치본과 소스는 v0.35.9 (`f31c756`)였고 저장 파일은 Wrike와 Background 모두 활성화였다. 과거 사용자 조작의 로그는 없어 최초 신고가 어느 설정 경로에서 발생했는지는 확정하지 않았다. 위 결함들은 격리된 회귀 시험으로 확인했다.

## 수정 범위

- Wrike 자동 UI는 기능 활성화와 Background 상태를 공통으로 검사한다. 이전 활성화 주기에서 예약한 콜백은 다시 켠 뒤에도 알림을 만들지 못한다.
- 비활성화 저장에 성공하면 자동 패널과 알림 타이머를 중단한다. 저장에 실패하면 기존 실행 상태를 유지한다.
- 설정 화면의 스위치는 단독으로 즉시 저장하고 실제 상태를 다시 읽는다. 다른 입력의 저장은 스위치 값을 포함하지 않는다.
- 대시보드도 스위치 값만 저장하고 실패를 표시한다. 열린 설정 화면은 다른 입력 초안을 보존하면서 스위치만 동기화한다.

## 검증 범위

직접 영향 단위시험, 변경된 Tk 상태의 native 시험, artifact-only task build와 clean tagged build를 사용한다. 전체 E2E와 무관한 UI는 실행하지 않는다. 설치본 배포는 transactional helper와 readiness 검증으로 별도 확인한다. 실행 결과와 설치본 identity는 릴리스 검증 보고서에 남긴다.

설치기 MinGW 자식 PATH 수정은 별도 작업 커밋으로 같은 version lane에 통합한다. 기존 단위시험과 독립 검토는 소스가 동일하면 재사용하며, 최종 설치기 제작은 통합된 tag에서 검증한다.
