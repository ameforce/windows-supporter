# 작업표시줄 UIA 조회 백그라운드 전환 hotfix

## 의도와 변경 분류

- 의도한 계약: 작업표시줄 오버레이의 위치 감시는 화면 스레드를 붙잡지 않아야 하며, 앱 창의 클릭과 스크롤은 즉시 반응해야 한다.
- 현재 동작: v0.33.13 이후에도 화면 스레드가 CPU를 약 12% 쓰고, 응답 지연이 가끔 수십 ms까지 늘어난다. 남은 화면 스레드 작업의 약 40%는 0.5초마다 작업표시줄 아이콘 위치를 UI 자동화(UIA)로 조회하는 부분이다.
- 차이: 다른 프로세스(탐색기)의 UIA 요소를 하나씩 읽는 조회가 화면 스레드에서 동기로 실행된다.
- 판정: 기존 응답성 계약을 복구하는 성능 결함 수정이므로 `hotfix/v0.33.14`로 분류한다.

## 근본 원인

`_detect_horizontal_taskbar_occupied_spans_with_debug`는 위치 감시 틱마다 `_uia_taskbar_occupied_span_records`를 호출한다. 이 함수는 작업표시줄 창의 UIA 하위 요소 전체를 찾은 뒤, 요소마다 화면 밖 여부, 종류, 경계 사각형, 식별자를 읽는다. 요소 하나를 읽을 때마다 탐색기 프로세스와 COM 왕복이 생긴다. 이 PC에서는 한 번에 약 34ms가 걸렸고, 좌우 오버레이가 이를 0.5초마다 화면 스레드에서 실행했다.

## 수정

- UIA 조회만 전담하는 백그라운드 수집기(`_UiaSpanSampler`)를 둔다. 작업 스레드를 시작하기 전에 호출 스레드에서 `comtypes`를 미리 가져오고, 작업 스레드는 `ole32.CoInitializeEx`로 다중 스레드 아파트(MTA)에 들어간 뒤 조회한다. `comtypes`는 처음 가져오는 스레드를 STA로 초기화하고 MTA 스레드에서는 가져오기가 실패하므로, 작업 스레드가 처음 가져오는 스레드가 되지 않게 한 것이다.
- 위치 틱은 같은 요청의 가장 최근 조회 결과를 즉시 받아 쓰고, 새 조회는 수집기에 요청만 한다. 따라서 오버레이 위치는 조회 한 번(0.5초 이내)만큼 늦게 반영될 수 있다.
- 결과가 2초보다 오래되면(전체 화면 억제 뒤 재개 등) 오래된 결과로 배치하지 않고 새 조회를 기다린다.
- 처음 보는 요청(앱 시작, 화면 구성 변경 직후)은 첫 배치가 아이콘을 가리지 않도록 결과를 최대 1.5초까지 기다린다. 시간을 넘기거나 조회가 실패하면 기존처럼 빈 결과로 처리하고, 자식 창과 화소 표본은 그대로 사용한다.
- 같은 요청의 반복 조회는 0.25초 간격으로 제한하고, 처음 보는 요청은 바로 처리한다.
- 동기 조회 함수 `_uia_taskbar_occupied_span_records`는 그대로 둔다.

## 결과

실제 작업표시줄에서 확인한 값이다.

| 항목 | 값 |
|---|---|
| 호출 스레드에서 직접 조회할 때 | 약 34ms |
| 수집기 첫 요청(결과 대기) | 약 167ms, 앱 시작이나 화면 구성 변경 때 한 번 |
| 수집기 이후 요청 | 최대 0.14ms |
| 두 방식의 아이콘 위치 목록 | 같음(30개) |

## 검증 범위

조회가 호출한 스레드가 아닌 다른 스레드에서 실행되는지 확인한다. 느린 재조회 중에도 호출이 막히지 않고 이전 결과를 돌려주는지, 처음 보는 요청이 시간을 넘기면 빈 결과였다가 이후 결과를 받는지, 오래된 결과는 새 조회를 기다리는지, 새 프로세스에서도 작업 스레드가 MTA에 들어가고 `comtypes`를 정상으로 쓰는지도 확인한다. 조회 실패, 복사본 반환, 서로 다른 요청의 결과 분리, 결과 캐시 상한, 위치 감지가 수집기를 거치는지 검증한다. 오버레이, 다중 모니터, 좌우 창, 작업표시줄 대상, 복구, 다중 모니터 관리자, 패키징 계약 시험을 실행한다.
